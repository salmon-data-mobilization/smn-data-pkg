## What changed, and where

One branch and one pull request, because `HUB.md` allows one draft pull request
per handed-back item. The dispatch brief allowed either one or two.

- **`.github/workflows/release.yml`** (new). A `workflow_dispatch` taking
  `version` (`0.3.1`, without the `sdp-` prefix) and `commit` (a full SHA). It
  pushes an annotated `sdp-X.Y.Z` tag on that commit and publishes a GitHub
  Release whose body is that version's `CHANGELOG.md` section as the commit has
  it. The design is metasalmonpy's `release.yml` on its `main` at `ba1b54a`:
  inputs reach the shell only through the environment, checks refuse rather
  than warn, the commit has to be on main's first-parent line, a rerun can
  finish a release whose tag was pushed before the release step failed, and
  every file is read from disk rather than through a pipe (the SIGPIPE that
  killed metasalmonpy's first real run). What differs:
  - **Tag and message.** The tag is `sdp-X.Y.Z`, annotated, with the message
    `Salmon Data Package spec sdp-X.Y.Z (see CHANGELOG)`. That is the form of
    the existing `sdp-0.2.0` and `sdp-0.3.0` tags, both annotated with messages
    in that style.
  - **What made the version current.** smn-data-pkg has no version file to
    compare, so the commit that made X.Y.Z current is the first commit on
    main's first-parent line whose `CHANGELOG.md` has the heading. At the
    commit there must be exactly one `## [sdp-X.Y.Z]` heading, reading
    `## [sdp-X.Y.Z] - YYYY-MM-DD` as `sdp-0.3.0`'s does, and the first parent
    must have none.
  - **The profile check.** The commit's current profile is the one
    `schema/sdp.rules.yaml` names in `profile:`. That URL has to end in
    `profiles/salmon-data-package/vX.Y/profile.json` for the tag's X.Y, the
    file has to exist at the commit with that URL as its `$id`, and its
    `sdp:version` has to be in `sdp-X.Y.*`. So a patch tag has to sit on a
    commit whose profile is still v0.3. Only the family is compared, and the
    first question under *Needs Brett* is why.
  - **Two refusals metasalmonpy's does not have.** It refuses entries still
    under `[Unreleased]` at the commit, because they are in the tree the tag
    names but would be left out of its notes. It also refuses a dispatch from
    any branch but `main`, because a dispatch from another branch runs that
    branch's copy of the checks.
- **`CHANGELOG.md`**. First, the CI entry under `[Unreleased]` loses "No release
  automation.", and a release-workflow entry is added. Then the release commit
  files everything under `[Unreleased]` beneath a new
  `## [sdp-0.3.1] - 2026-09-25` heading, with `[Unreleased]` left empty above
  it. **That release commit changes two lines and nothing else.**
- **`.github/workflows/ci.yml`**: the header comment "Deliberately no release
  automation." now points at `release.yml`.
- **`AGENTS.md`**: a three-line *Releases* section that points at the
  workflow's header.

## Needs Brett

1. **Should `sdp-0.3.1`'s tree say `sdp-0.3.1`?** At the tag it will still say
   `sdp-0.3.0` in four places: `schema/sdp.rules.yaml` `version:`, the
   generated v0.3 profile's `sdp:version`, both examples'
   `spec_version`/`specVersion`, and the `spec_version` example string in
   `dataset.schema.json`. At `sdp-0.2.0` and `sdp-0.3.0` the rules `version:`
   equalled the tag. It matters downstream. metasalmon's
   `.ms_sdp_profile_version()` (`R/schema-helpers.R`) requires the rules
   `version` and the profile's `sdp:version` to match, and writes that value
   into `dataset.csv` wherever `spec_version` is blank. So once B-198 vendors
   this tag, a package whose `temporal_start` uses the instant 0.3.1 admits
   would declare `sdp-0.3.0` by default, and 0.3.0's pattern rejects that
   instant. **Recommendation: bump
   before the merge, in this pull request.** Set `version: sdp-0.3.1` and run
   `python scripts/generate_artifacts.py --write`. Measured in a scratch
   checkout, that changes one line in each of three files: the rules, the
   profile and `docs/field-reference.md`. Tests and `--check` stay green, and no
   path or URL changes. The examples are optional hand edits. It cannot be done
   after the tag, and the workflow accepts either answer, because it compares
   only the family.
2. **`sdp-0.3.0` has no GitHub Release.** smn-data-pkg has no releases at all.
   Once this merges, the workflow can publish one for `0.3.0` at `48c0e77`
   without moving the hand-made tag: it accepts the existing annotated tag and
   publishes only. This is tested above as the 0.3.0 run. That is an outward
   act, so it is his to ask for. Backfilling `sdp-0.2.0` is not possible this
   way, because its changelog has no heading for it.
